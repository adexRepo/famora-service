# Famora Service Agent Guide

## Project overview

- Java 21, Spring Boot 4.0.6, and Maven (`pom.xml`). There is no Maven wrapper; use the installed `mvn` command.
- This is a single Spring Boot application organized package-by-feature under `com.famora`, not Spring Modulith and not a multi-module Maven build.
- Primary features are `auth`, `user`, `family`, `vault`, `document`, `backup`, `finance`, `business`, `note`, `tracker`, `notification`, `emergency`, `dashboard`, and `prayer`. Shared infrastructure lives in `common`, `security`, `audit`, `file`, and `currency`.
- PostgreSQL is the only configured database. JPA/Hibernate uses the `famora` schema with Open Session in View disabled and schema generation disabled.
- Flyway owns schema changes through `src/main/resources/db/migration`. New migrations use the current `V1_0_NN__description.sql` sequence; never edit an already-deployed migration.
- HTTP APIs use the `/api/v1` prefix under the configured `/famora` servlet context. Most successful responses use `ApiResponse<T>`; large lists use `PageResponse<T>`.
- Authentication uses JWT access tokens, hashed refresh-token sessions, BCrypt passwords, and `CurrentUserProvider`. Family context is selected through `X-Family-Id`; business context is selected by a path `businessId` and checked through `BusinessPermissionService`.
- Important current security fact: `SecurityConfiguration` permits all requests at the filter-chain rule level. The JWT filter authenticates valid bearer tokens, while controllers/services enforce the caller and resource permissions. New protected flows must perform explicit authentication and ownership/membership checks; do not assume the URL rule protects them.
- Audit records are written asynchronously with a dedicated executor and `REQUIRES_NEW`. Family modules normally use `AuditLogService`; business modules use `BusinessAuditPublisher`.
- File workflows support MinIO and local/MFT paths through `StorageService`. Documents and daily-report photos use file assets; backup supports resumable upload sessions and temporary chunks.
- External HTTP integrations use Spring `RestClient`: Frankfurter currency rates and Aladhan prayer times. Both currently use in-process Caffeine caches.
- Notifications use persisted records plus STOMP over WebSocket at `/ws`, publishing per-user messages to `/user/queue/notifications` after transaction commit.
- There is no active `@Scheduled` worker in the repository. Tracker notification rows are generated by service orchestration. The only background executor currently enabled is async audit writing.
- Tests use JUnit Jupiter and AssertJ, with Spring Boot test starters available. Existing automated coverage is currently small and should be expanded around changed behavior.
- No Dockerfile, Compose file, or repository CI/CD configuration is present. Runtime configuration is in `application.yml` and is overridden with environment variables.

Useful commands:

```powershell
mvn spring-boot:run
mvn -DskipTests compile
mvn test
mvn clean package
```

Application startup requires reachable PostgreSQL and, with the current storage configuration, MinIO. Supply real database, JWT, vault, and MinIO secrets through environment variables; never add production secrets to source control.

## Engineering principles

- KISS: choose the smallest implementation that correctly satisfies the current requirement. Prefer readable code over clever code.
- YAGNI: do not add speculative extension points, unused options, generic frameworks, unnecessary interfaces, or infrastructure for hypothetical needs.
- DRY: centralize repeated business knowledge, constants, and rules. Do not merge code merely because it looks structurally similar; a small amount of duplication is better than a false abstraction.
- Pragmatic SOLID: use boundaries that improve ownership, testability, or integration isolation. Do not mechanically create interfaces or layers.
- Avoid unrelated refactoring and dependency upgrades. Preserve public contracts unless the task explicitly changes them.
- Before changing code, inspect the surrounding module, trace the full request/event path, inspect its tests and migrations, identify the smallest correct change, then add meaningful verification.

## Architecture rules

### Controllers

- Keep controllers in the owning feature package. Receive transport input, apply Bean Validation, resolve family/current-user context, call services, and return HTTP semantics.
- Do not put business rules, persistence queries, or substantial mapping logic in controllers.
- Follow established routes, `ApiResponse`, `PageResponse`, `PagingHelper`, and `ResponseEntity` conventions. Return `201 Created` where the surrounding create endpoints already do so.

### Services

- Services own use-case orchestration, business rules, authorization, audit calls, integration coordination, and transaction boundaries.
- Keep family/business resource checks in the execution path. An ID, request header, or frontend control is never proof of access.
- Use `@Transactional` for complete atomic writes and `@Transactional(readOnly = true)` for non-trivial reads when consistent with the module. Do not hold a database transaction open across slow storage or external HTTP calls without evaluating compensation and consistency.
- Avoid catch-all services. Keep ownership within the feature package and prevent circular cross-module dependencies.

### Entities and DTOs

- New persistent entities should follow the existing hierarchy where applicable: `BaseEntity`, `AuditableEntity`, `FamilyScopedEntity`, `VisibleFamilyScopedEntity`, or `BusinessScopedEntity`.
- Auditable feature data normally has `createdAt`, `createdBy`, `updatedAt`, `updatedBy`, and `status`. Set `updatedBy` on mutations and use soft-delete status where the module already does.
- Keep transport concerns out of entities. Use request/response DTOs for new public contracts; records are preferred for simple immutable DTOs.
- Mapping is predominantly explicit constructors/static mapping methods. MapStruct dependencies exist but there are no active `@Mapper` implementations; do not introduce a second mapping style without a clear benefit.

### Repositories

- Use Spring Data derived methods and `JpaSpecificationExecutor` for composable optional filters.
- Keep family/business/status predicates in every resource query. Scope by both resource ID and owner scope to prevent IDOR.
- Use custom JPQL/native query repositories only for justified aggregation, union, reporting, or performance-sensitive reads. Bind parameters; never concatenate untrusted values into SQL.
- Repositories expose persistence operations, not business decisions.

### Integrations

- Keep external HTTP, WebSocket publishing, audit delivery, and object storage behind their existing services.
- Use grouped `@ConfigurationProperties` for cohesive new configuration where practical. Keep secrets in environment variables.
- Account for timeout, failure mapping, cache behavior, idempotency, and transaction timing at integration boundaries.

## Java and Spring standards

- Use constructor injection. Do not add field injection, raw generic types, wildcard imports, silent exception swallowing, unexplained magic values, or commented-out production code.
- Prefer meaningful names, immutable DTOs, explicit null handling, and focused constants/enums for shared domain values.
- Do not create single-implementation interfaces unless they represent a real integration boundary, alternate implementation, or useful test contract.
- Do not create `Util`, `Helper`, `Manager`, or `Processor` dumping grounds. Existing focused helpers may be extended only when the responsibility remains cohesive.
- Validate untrusted transport input with Jakarta Bean Validation and add business validation in services.
- Use `GlobalExceptionHandler` and the established module exception type (`AppException`, `BusinessException`, `FamilyException`, or a specific exception). Preserve stable external error codes where present and never expose stack traces, filesystem paths, SQL details, or raw internal exceptions.
- Do not expose lazy JPA associations through serialization. Keep `spring.jpa.open-in-view=false` assumptions intact.

## API and security standards

- Preserve `/api/v1` routes and backward compatibility unless a contract change is requested. Use intentional request/response fields and appropriate HTTP methods/statuses.
- Paginate every potentially large collection and cap page sizes through the existing paging helper/pattern.
- For every endpoint, evaluate authentication, family/business isolation, role, creator/owner policy, IDOR, mass assignment, sensitive fields, and audit requirements.
- For sensitive modules (`vault`, `document`, `backup`, `finance`), minimize list payload exposure and require detail/reveal/download authorization separately.
- Never log passwords, bearer or refresh tokens, encryption keys, vault secrets, complete documents, file bytes, or full financial/personal payloads.
- For uploads, enforce request and domain size limits, inspect file signatures rather than trusting MIME/extension, sanitize names and paths, prevent traversal, scope object keys, and authorize downloads/deletes.
- Evaluate brute force, abuse/rate limits, replay/idempotency, race conditions, and privilege escalation for shared-state workflows.

## Persistence, migrations, and transactions

- Inspect the latest migrations, affected entities, repositories, and actual access paths before designing schema changes.
- Add forward-only Flyway migrations for every schema change. Preserve existing data, nullability compatibility, foreign keys, and rollback/operational safety.
- Add indexes only for real query predicates/orderings. Consider uniqueness and concurrency at the database level when application checks can race.
- Watch for N+1 reads, unbounded loads, accidental lazy loading, and oversized JSON/file metadata. Choose specifications, projections, fetch joins, or custom queries based on the use case rather than applying one strategy globally.
- Transactions protect database atomicity only. For WebSocket messages use after-commit publication; for async audit use the existing writer; for storage/external effects design explicit failure cleanup or reconciliation.

## Audit, logging, caching, and storage

- Record meaningful create/update/delete/reveal/download/workflow actions except where product policy explicitly excludes audit. Keep metadata minimal and non-sensitive.
- Preserve `X-Correlation-Id` handling and include resource IDs and operations in useful logs. Avoid noisy loop logging.
- Caffeine caches are local to one instance. Do not treat them as shared consistency or locking. Define key, TTL, invalidation, failure fallback, and multi-instance implications before adding a cache.
- Preserve storage metadata such as original name, original/resolved MIME type, extension, size, hash, storage type, bucket/key/path, and family/business ownership.
- Resumable backup changes must preserve chunk idempotency, checksum validation, isolated temp paths, safe assembly, cancellation, and cleanup after completion/failure.

## Testing and dependency policy

- Prioritize tests for business rules, authorization and isolation, regressions, transaction behavior, concurrency-sensitive invariants, edge cases, and integration boundaries.
- Prefer focused unit tests for pure logic and repository/web/integration tests when framework behavior or database constraints matter. Avoid excessive mocking and private implementation assertions.
- A bug fix should normally include a regression test when practical. Do not add tests for trivial accessors merely to increase coverage.
- Before adding a dependency, check existing project code, Java 21, and Spring Boot capabilities. Add only maintained, compatible libraries that materially simplify the required behavior.

## Verification

- Run the narrowest relevant test first, then `mvn test` for changes with shared or cross-module impact.
- Run `mvn -DskipTests compile` after source changes and `mvn clean package` when release packaging matters.
- Review every new Flyway migration against existing schema and startup behavior.
- Run `git diff --check` and inspect `git diff` before completion. Never report a check as passed unless it was executed; clearly state checks that could not run.
